# 长源文件与长输出工作流规范

本规范用于“源文件/资料 + 提示词”共同发送给模型的接入任务。它解决的不是单纯网络超时，而是上下文、输出上限、结构化结果和恢复问题。

## 1. 不要一次性要求模型返回全部结果

当用户提供的源文件较大，或任务要求生成需求表、配置表、测试用例、代码补丁等大量结果时，默认采用分阶段工作流：

```text
读取文件清单与摘要
  ↓
确认处理范围和输出预算
  ↓
按章节、来源、需求 ID 等语义单元分批
  ↓
每批生成结构化结果或增量补丁
  ↓
本地校验和归一化
  ↓
保存检查点
  ↓
聚合、去重、校验并激活结果
```

不要按字符数机械切割源文件，避免切断代码、配置、规则、引用或章节关系。

## 2. 提示词合同

发送给模型的请求应明确区分：

1. 任务目标：本次只完成一个阶段职责。
2. 输入范围：列出文件、章节、来源 ID 或本批语义单元。
3. 事实边界：只能使用输入证据，缺失事实必须标记，不得猜测。
4. 输出 Schema：字段、类型、枚举、数量和 ID 关联规则。
5. 输出预算：不要重复输入源文件，不要输出无关解释、完整文件回显或 Markdown 包装。
6. 失败合同：达到输出上限时返回已完成范围、未完成范围和截断标记。

推荐的通用请求结构：

```text
你正在执行阶段：{stage_name}。
目标：{single_stage_goal}
输入文件/范围：{source_manifest_and_scope}
上游已确认结果：{minimal_upstream_context}
事实边界：只使用输入证据；无法确认时返回 needs_review，不要编造。
输出格式：严格遵守 {schema}，只返回本批结果。
输出限制：不复述源文件，不输出分析过程，不生成未要求的字段；达到限制时返回 truncation=true 和已完成 ID。
完成标准：{acceptance_criteria}
```

源文件应通过文件引用、分批内容或受控上下文传入，不要在每一批重复携带无关的全部历史结果。

## 3. 输入和输出预算

输入长度和输出长度是两个独立问题：

- 输入没有超过上下文窗口，不代表输出一定能容纳全部结果；
- 增大网络超时不能解决输出 Token 上限；
- 增大 `max_tokens` 不能保证服务商允许同样的上限；
- 预检提示词、源文件、上游结果和预留输出的总预算；
- 预算不足时优先减少本批语义范围，而不是盲目压缩或截断源文件。

所有预算值必须可配置，不要把某个项目的 Token 数、批量大小或调用次数写成通用固定值。

## 4. 截断与自适应分批

保存并识别 `finish_reason=length`、响应长度和服务商诊断。

当输出被截断或输入预算超限时：

1. 如果当前批有多个语义单元，按语义边界二分；
2. 成功批次立即保存检查点；
3. 如果单个语义单元仍超限，停止自动扩大请求，提示用户缩小范围、降低输出密度或更换模型；
4. 不重复执行已经成功保存的批次。

## 5. 结构化输出修复

按以下顺序处理：

1. 去除代码围栏等纯包装差异；
2. JSON 解析和 Schema 校验；
3. 本地执行确定性的无损归一化；
4. 对纯格式缺陷最多发起一次受约束修复；
5. 仍失败则保存原始脱敏证据并标记人工复核。

本地可以补齐的字段不得再次交给模型猜测。模型修复不能新增、删除或改写业务事实，也不能把校验上下文、`allowed_*` 或错误包装字段回显成业务结果。

## 6. 幂等、检查点与结果激活

运行指纹至少由源文件内容、人工补充、模型、Prompt/Skill 版本和配置快照组成。相同指纹已有成功结果时，默认复用或要求用户明确重跑。

每个批次完成后保存：批次 ID、输入范围、输出、Schema 校验、Token、耗时和错误信息。恢复运行时只处理未完成范围。

完整运行成功必须同时完成：

1. 保存结果；
2. 更新当前活动结果；
3. 前端立即使用本次请求返回结果更新界面。

后台 GET 只能作为无缓存二次校准，不能让前端重新显示旧的本地缓存、旧筛选或旧分页。

## 7. 取消与重试

- 鉴权、权限、无效模型和确定性 Schema 失败不得盲目重试；
- 429、短暂连接中断和明确的 5xx 才能按有限次数重试；
- 正常调用、重试和格式修复共享总调用上限；
- 用户取消必须能中断请求、退避等待和下一批调度；
- 失败和部分完成状态必须保留，不能重置成“尚未执行”。
